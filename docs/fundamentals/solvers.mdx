# Solvers

The linear system solver is selected with `model.setSolverMethod(solverMethod)`. If it is not set, FEAScript uses
`"lusolve"`.

```javascript
model.setSolverMethod("frontal");
```

| `solverMethod` | Method                                                                | Called with          |
| -------------- | --------------------------------------------------------------------- | -------------------- |
| `"lusolve"`    | Sparse LU decomposition (direct, from [math.js](https://mathjs.org/)) | `solve()`            |
| `"jacobi"`     | Jacobi iteration on the CPU                                           | `solve()`            |
| `"frontal"`    | Frontal solver (direct, element by element)                           | `solve()`            |
| `"jacobi-gpu"` | Jacobi iteration on the GPU with WebGPU                               | `await solveAsync()` |

## Supported combinations

| Model                             | `"lusolve"` | `"jacobi"` | `"frontal"` | `"jacobi-gpu"` |
| --------------------------------- | :---------: | :--------: | :---------: | :------------: |
| `heatConductionScript`            |      ✓      |     ✓      |      ✓      |       ✓        |
| `generalFormPDEScript`, linear    |      ✓      |     ✓      |      ✓      |                |
| `generalFormPDEScript`, nonlinear |      ✓      |     ✓      |             |                |
| `frontPropagationScript`          |      ✓      |     ✓      |      ✓      |                |
| `creepingFlowScript`              |      ✓      |            |             |                |
| `eulerBernoulliBeamScript`        |      ✓      |     ✓      |             |                |

For the nonlinear models (`frontPropagationScript`, and `generalFormPDEScript` with `nonlinear: true`), the
selected method solves the linear system of each Newton–Raphson iteration.

The creeping flow system has zero diagonal entries in its pressure rows, so the Jacobi method cannot be applied
to it; use `"lusolve"`.

## LU decomposition (`"lusolve"`)

The default method. The assembled sparse matrix is factorized with the sparse LU decomposition of math.js
(with partial pivoting) and the system is solved directly. It works for every model and needs no tuning, so it
is a good first choice.

Before factorizing, the columns are reordered to limit the fill-in, the new nonzero entries that the
decomposition creates. Each model uses the ordering that suits its matrix: an approximate minimum degree
ordering of $\mathcal{J} + \mathcal{J}^T$ for the symmetric-like matrices of most models, and of
$\mathcal{J}^T \mathcal{J}$, with a relaxed pivoting threshold, for the creeping flow matrix, whose pressure
rows have zeros on the diagonal.

## Frontal solver (`"frontal"`)

The frontal solver assembles and eliminates the equations element by element, so only the equations of the
active "front" are kept in memory instead of the whole matrix. Dirichlet conditions and, for heat conduction,
convection conditions are applied during the assembly of each element.

The memory and run time grow with the width of the front, which depends on the order in which the elements are
assembled. FEAScript compares a few element orders (the order of the mesh, sweeps along $x$ and $y$, and a
breadth-first order through neighboring elements) and uses the one with the narrowest front, so the front
sweeps across the short side of the domain, also on unstructured Gmsh meshes.

## Jacobi method (`"jacobi"`)

An iterative method: at each iteration, every unknown is updated from the values of the previous iteration,

$$
u_i^{(m+1)} = \frac{1}{\mathcal{J}_{ii}} \left( R_i - \sum_{j \ne i} \mathcal{J}_{ij} \, u_j^{(m)} \right),
$$

starting from $\bar{u}^{(0)} = 0$. The iterations stop when the residual, relative to the right-hand side, is
smaller than the tolerance:

$$
\frac{\lVert \bar{R} - \mathcal{J} \bar{u}^{(m)} \rVert_2}{\lVert \bar{R} \rVert_2} < \text{tolerance}.
$$

The size of the change between two iterations is not used: the Jacobi method can converge slowly, so the changes
become small while the iterate is still far from the solution.

The Jacobi method converges only for suitable matrices, for example diagonally dominant ones. Linear elements
usually give such matrices; quadratic elements usually do not. If the method does not converge, FEAScript logs
an error and returns the last iterate.

| Option          | Default | Description                                     |
| --------------- | ------- | ----------------------------------------------- |
| `maxIterations` | `10000` | Maximum number of Jacobi iterations             |
| `tolerance`     | `1e-8`  | Tolerance on the residual relative to $\bar{R}$ |

These options can be passed to `solve()` or `setModelConfig()` (see
[`FEAScriptModel`](../api/feascript-model.md)):

```javascript
model.setSolverMethod("jacobi");
const result = model.solve({ maxIterations: 200000, tolerance: 1e-8 });
```

## Jacobi method on the GPU (`"jacobi-gpu"`)

The same Jacobi iteration, run on the GPU with [WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)
through [taichi.js](https://taichi-js.com/), in a separate web worker. It is used through the asynchronous
`solveAsync` method and is currently available for `heatConductionScript` only:

```javascript
model.setModelConfig("heatConductionScript");
// ...mesh and boundary conditions...
model.setSolverMethod("jacobi-gpu");
const result = await model.solveAsync();
```

:::caution
`"jacobi-gpu"` runs only in browsers that support WebGPU, and the GPU kernel works on a **dense** copy of the
system matrix, so its memory use grows with the square of the number of nodes.
:::

The GPU computations use single precision (32-bit) floats. The `maxIterations` option (default `10000`) has the
same meaning as for `"jacobi"`. The `tolerance` option (default `1e-4`) applies to a different stopping criterion:
the largest absolute residual, $\max_i \lvert R_i - \sum_j \mathcal{J}_{ij} u_j \rvert$, which is checked every few
iterations.

## Newton–Raphson method

Nonlinear models are solved with the Newton–Raphson method (see
[Finite element method](./finite-element-method.md#linear-and-nonlinear-systems)). It starts from
$\bar{u} = 0$ and stops when $\lVert \Delta \bar{u} \rVert_2$ is smaller than or equal to the tolerance. If the
norm of an increment exceeds $10^2$, the iterations are stopped and an error is logged.

| Option          | Default | Description                                   |
| --------------- | ------- | --------------------------------------------- |
| `maxIterations` | `100`   | Maximum number of Newton–Raphson iterations   |
| `tolerance`     | `1e-4`  | Tolerance on $\lVert \Delta \bar{u} \rVert_2$ |

For `generalFormPDEScript`, these options apply to the Newton–Raphson iterations and the inner linear system
uses the defaults of the selected method. For `frontPropagationScript`, see the
[model page](../models/front-propagation.md#solution-procedure).

## Performance

The time FEAScript takes to assemble and solve a problem depends on the solver and on the size of the mesh. The
plot shows it for `"frontal"`, `"lusolve"` and `"jacobi"` on the [fin in 2D](../examples/heat-conduction.md#fin-in-2d),
with linear quadrilaterals on meshes from 20 × 10 to 320 × 160 elements. The `"jacobi"` line stops at 861 nodes:
on the larger meshes it does not converge with its default settings (see below).

![Fin in 2D: assembly and solve time of "frontal", "lusolve" and "jacobi" against the number of nodes, logarithmic axes; the "jacobi" line stops at 861 nodes](/assets/solver-performance.svg)

| Mesh      | Nodes  | `"frontal"` | `"lusolve"` | `"jacobi"`    | Elmer (UMFPACK) |
| --------- | ------ | ----------- | ----------- | ------------- | --------------- |
| 20 × 10   | 231    | 0.019 s     | 0.050 s     | 0.016 s       | < 0.01 s        |
| 40 × 20   | 861    | 0.092 s     | 0.10 s      | 0.063 s       | < 0.01 s        |
| 80 × 40   | 3,321  | 0.13 s      | 0.18 s      | not converged | 0.01 s          |
| 160 × 80  | 13,041 | 0.37 s      | 0.51 s      | not converged | 0.04 s          |
| 320 × 160 | 51,681 | 2.4 s       | 2.0 s       | not converged | 0.21 s          |

`"frontal"` is the faster direct solver up to about 13,000 nodes, and `"lusolve"` on the largest mesh. Both give
the same temperatures, to within 1e-10.

`"jacobi"` is the fastest on the two smallest meshes, but with its default settings it does not converge on the
larger ones: the number of iterations it needs grows with the mesh, and from 3,321 nodes it is more than the
default `maxIterations` of 10,000. Raising `maxIterations` lets it converge, but slowly: 10,111 iterations and
0.48 s on the 80 × 40 mesh, and 37,430 iterations and 6.2 s on the 160 × 80 mesh, against 0.13 s and 0.37 s for
`"frontal"`. Use it for small problems only. Where it converged, its temperatures differ from those of the
direct solvers by up to 7e-5 °C on these two meshes, because it stops at the residual tolerance.

The memory a problem needs also grows with the mesh. The plot shows the peak memory of the whole Node.js process,
which includes about 60 MB for Node.js and FEAScript themselves:

![Fin in 2D: peak memory of "frontal", "lusolve" and "jacobi" against the number of nodes, logarithmic axes; the "jacobi" line stops at 861 nodes](/assets/solver-memory.svg)

| Mesh      | Nodes  | `"frontal"` | `"lusolve"` | `"jacobi"`    | Elmer (UMFPACK) |
| --------- | ------ | ----------- | ----------- | ------------- | --------------- |
| 20 × 10   | 231    | 61 MB       | 66 MB       | 57 MB         | 30 MB           |
| 40 × 20   | 861    | 70 MB       | 67 MB       | 63 MB         | 31 MB           |
| 80 × 40   | 3,321  | 72 MB       | 82 MB       | not converged | 35 MB           |
| 160 × 80  | 13,041 | 97 MB       | 140 MB      | not converged | 51 MB           |
| 320 × 160 | 51,681 | 255 MB      | 346 MB      | not converged | 121 MB          |

From about 3,000 nodes, `"frontal"` needs less memory than `"lusolve"`, about three quarters of it on the
largest mesh.

Creeping flow is solved with `"lusolve"` only, and its time and memory grow faster with the mesh: on the
[lid-driven cavity](../examples/creeping-flow.mdx#comparison-with-elmer), 1.3 s and 219 MB on a 32 × 32 mesh
(4,225 nodes), and 10 s and 731 MB on a 64 × 64 mesh (16,641 nodes). The pressure rows of its matrix have zeros
on the diagonal, so its LU decomposition fills in more than that of heat conduction, even with the ordering that
suits it (see [LU decomposition](#lu-decomposition-lusolve)).

These numbers are from FEAScript-core 0.4.0 (RC), loaded from its built bundle in Node.js 18, on one core of an
AMD Ryzen 5 9600X. Each is the median of 5 runs, and the times include mesh generation. On another computer, or in
a browser other than Chrome, the times differ, but the comparison between the solvers holds.

The last column of each table gives the time and memory of [Elmer](https://www.elmerfem.org/), the open-source finite element
software of CSC – IT Center for Science, on the same meshes, as a reference. Elmer was run on one core, as a single
MPI process, so that both programs solve on the same terms. Elmer is a parallel program built for much larger
problems, typically in 3D, and this setup does not show its parallel performance. The benchmarks, with the Elmer
setups, are in [FEAScript-benchmark](https://github.com/FEAScript/FEAScript-benchmark).
